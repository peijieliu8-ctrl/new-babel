# New Babel：从共创画布到事项推进工作台

## 产品判断

无限画布的价值是减少跨部门事项中的重复解释、等待和责任空缺。画布保留发散讨论；事项、决策和任务对象承接收敛与执行。管理、复核和审批角色仍由人承担。本版继续用虚构数据和模拟 Agent 验证交互，不宣称已实现企业身份、正式审批或业务提效。

## 首个验证场景

选用“一个字段反复确认”：业务提出字段口径与页面表现问题，技术补充实现约束，参与者共同核对依据版本，负责人记录取舍，任务负责人提交交付结果，另一人复核验收。

这个场景的阻塞点是各方反复确认的对象和依据不一致。若问题属于“数据到底由谁交付”，画布可以显露责任缺口，但仍需机构明确数据责任、授权和交付规则。

## 工作对象与视图

| 对象 | 必须回答的问题 | 结果 |
| --- | --- | --- |
| 事项 | 要解决什么、为何重要、谁负责推进、当前卡在哪里？ | 唯一的协作入口和当前状态 |
| 证据 | 信息从哪里来、适用哪个版本、由谁核验？ | 决策可回溯；来源变化可触发复核 |
| 异议 | 哪个观点未被回应、会影响什么？ | 决策者能看见分歧，而非只看摘要 |
| 决策 | 有哪些方案、取舍理由是什么、谁作了确认？ | 留下人工确认的决策记录 |
| 任务与验收 | 谁执行、何时交付、提交了什么、谁复核？ | 决策有可检查的交付结果 |

| 视图 | 主要用途 |
| --- | --- |
| 画布 | 展开问题、证据、异议和方案之间的关系 |
| 待我处理 | 看见当前需要本人确认、执行或复核的事项 |
| 决策清单 | 追踪待决策、已决策和需要重新核验的事项 |
| 时间线与复盘 | 查看状态变化、交接、决策与验收记录 |

所有视图读取同一份服务端画布状态，不产生各自独立的事实版本。

## 人与 Agent 的分工

| 工作 | 负责方 |
| --- | --- |
| 提出目标、指派责任、决定取舍、批准、验收 | 有相应职责的人 |
| 提示材料变化、整理分歧、指出缺少的依据、起草摘要 | Agent 辅助；结果标注来源和模拟属性 |
| 超时提示、状态门槛、版本冲突检查 | 确定性的 Workflow 规则 |
| 读取或修改其他系统 | 本版不接入；未来须按用户身份、具体任务和动作风险授权 |

MCP 是工具连接方式，不提供机构身份和审批权；沙箱限制执行环境，也不能替代数据授权。未来若接文件、浏览器或内网系统，需记录工具调用、输入输出范围、人工确认和中断或恢复路径。

## 本版验收重点

1. 两位参与者可在同一事项中记录来源、分歧、人工决策和任务验收；刷新后仍能复盘。
2. 决策所依赖的证据及其版本可定位；关键来源变化后，不继续把旧决定显示为无条件有效。记录新决策后，旧决策下已提交或已验收的任务退回，负责人需重新提交，复核人再次验收。
3. 未形成必要的人工决策、责任分配或当前决策下的验收时，不能把事项宣布为完成；本版仅由事项负责人昵称代演完成确认。
4. 自动演示可展示上述闭环，同时持续标明角色、Agent 结果与确认均为脚本模拟；暂停、重播和手动接管继续可用。
5. 普通画布的两人同步、单卡编辑锁、个人 Agent 私下预览和版本冲突保护继续可用。

## 金融机构真实试点门槛

当前昵称与房间链接仅用于演示，不是身份或访问控制。真实业务数据进入前，至少要完成统一身份、事项与资料级授权、数据分级、留存规则、正式审批对接、操作审计和版本恢复。AI 建议必须与人工决策有明确区分。具体流程及监管适用范围应由机构的业务、科技和合规部门共同确认。

## 效果验证

先选同类历史事项建立基线，再比较试点。核心指标为事项从提出到业务验收的总耗时；辅助指标为交接等待时间、重复确认轮次、按时明确责任人的比例、证据可追溯率和返工次数。演示中的过程计数不能推算真实节省的人力或费用。
